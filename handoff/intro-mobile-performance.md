# 介绍页手机滚动性能排查 · 2026-11-16

现象：在手机 Chrome 和 Safari 中滚动介绍页时能感到卡顿，微信内浏览器体感更流畅。本轮排查基于实验分支 `dcf6a27` 与线上发布提交 `508b2f6`，只做诊断。

在 [线上介绍页](https://yuchen.ink/blog/intro/) 用 iPhone Safari、Chrome、微信的浏览器标识请求，三组返回的 HTML、两份 CSS 和页面脚本分别一致。线上与本地肖像、书架 CSS 一致，发布仓库的滚动实现也与本地一致。线上根路径会根据当前浏览器是否已看完介绍，分别跳往介绍或书架；复测请在三个应用里都直接打开 `/blog/intro/`。

## 可确认的开销

在 MacBook Pro（M1 Pro）的桌面 Chrome 中模拟 390×844、3 倍像素比的视口。等图片解码后，按同样的滚动轨迹从顶部走到书架露出的末段，用时约 5.1 秒。对照只把四幕的聚光参数固定到最大值，保留遮罩本身、滚动脚本、位移、淡入和书架转场。每组各三次，交替顺序。

| Chrome 记录 | 原版 | 固定聚光 |
| --- | ---: | ---: |
| Paint 事件数（各三次一致） | 391 | 132 |
| Paint 累计时间（三次中位数） | 32.10 ms | 7.11 ms |
| 帧回调间隔 P95 | 16.7–16.8 ms | 16.7 ms |

同尺寸的桌面无界面 WebKit 跑了同一组对照。原版与固定聚光的帧回调中位间隔均为 33 ms，连空白页也是 33 ms。因此这一环境的刷新节奏无法区分两组性能，也不能当作手机 Safari 的帧率。

- [聚光遮罩](../homepage/styles/portrait.css#L234)：开场和中间两幕把动态径向渐变与静态线性遮罩相交；合照也动态修改径向遮罩。固定聚光后绘制事件减少约 66%，差异出现在四幕肖像阶段。这个对照定位了额外绘制的来源；模拟测试原版没有复现明显掉帧，不能用结果推算手机上的 FPS。
- [滚动回调](../homepage/scrollScenes.js#L28)：已有被动监听和每帧合并，滚动时仍会读取两处边界并尝试写入 30 项 CSS 变量，也更新不在场的镜头。Chrome 轨迹中实际布局仅两次，持续开销集中在样式更新和后续绘制，而非反复完整布局。React 未随每次滚动更新状态。
- [合照退场](../homepage/styles/portrait.css#L206)：转场时大幅肖像上移，动态阴影变化，下面的书架开始露出。固定聚光后，这一段的绘制事件数不变。额外隐藏书架的一次对照中，退场阶段的栅格任务数下降（781 → 173），累计耗时接近（约 42–43 ms）；不能据此认定书架造成掉帧。若真机主要在最后一段卡，优先隔离阴影与书架。
- [照片加载](../homepage/PortraitScene.jsx#L6)：四张 WebP 合计约 261 KiB，若各按原始尺寸以 4 字节/像素展开，总像素约合 18 MiB；这是尺寸估算，并非进程内存实测。解码和图层准备可以影响初次进入，不能解释预先解码后仍可观察到的反复绘制。

## 下一步如何定因

在同一台手机依次打开相同直达链接，等图片加载后重复滑动，记录最卡的是开场点灯、中间两次转身、合照点亮，还是合照退场。分别试地址栏刚展开和已收起的状态。页面主要使用 `svh`，不宜仅凭现象断言地址栏变化导致持续重排；应用的滚动事件节奏和浏览区域仍是待验证的变量。若仍能复现，连接 Mac 用 [Safari Web Inspector](https://webkit.org/web-inspector/enabling-web-inspector/) 录制 [渲染帧](https://webkit.org/web-inspector/timelines-tab/)，先对比原版和固定聚光，若卡在退场再隔离阴影与书架。用真机结果决定移动端是否把聚光改为渐变叠层的缩放与淡入，同时保留原分镜。
